Ansibleのきほん

ansible-skeleton guide

サーバー設定を、手順書ではなくコードで。

Ansible（アンシブル）は、複数のサーバーに対する設定作業を YAMLファイルに書いて自動実行するツールです。このガイドでは、リポジトリ ansible-skeleton の実際のファイルを教材に、Ansibleのしくみを予備知識ゼロから説明します。

STEP 1

Ansibleとは何か

サーバーを1台セットアップするとき、普通は SSH でログインして yum install vim のようなコマンドを順に打ちます。これが10台、50台になると、同じ作業の繰り返しになり、打ち間違いや「この1台だけ設定が違う」という事故が起きます。

Ansible は、その一連の作業を 「あるべき状態」としてファイルに書いておき、コマンド一発で全サーバーに適用するツールです。

手元のPCコントロールノード
Ansibleはここだけに入れる
──────▶SSH で接続して実行
Webサーバー 1エージェント不要
Webサーバー 2エージェント不要
DBサーバーエージェント不要

Ansible の大きな特徴が3つあります。

AGENTLESSサーバー側に何も入れない

接続はふだん使っている SSH をそのまま使います。サーバー側に常駐ソフト（エージェント）のインストールは不要で、SSH でログインできるサーバーなら今すぐ対象にできます。

YAML設定は読めるテキスト

「何をするか」は YAML という人間が読みやすい形式で書きます。プログラミングというより、構造化された手順書に近い見た目です。Git で差分管理・レビューもできます。

IDEMPOTENT何度実行しても安全

「vim を入れる」ではなく「vim が入っている状態にする」と書きます。すでにその状態なら何もしないため、同じコマンドを何度実行しても結果は同じです（冪等性・べきとうせい）。

STEP 2

3つの登場人物

Ansible を使ううえで最初に覚える概念は3つだけです。

名前役割ひとことで言うと
インベントリ
inventories/		操作対象のサーバー一覧。接続先ホスト名・ユーザー・ポートを書き、web のようなグループにまとめる。「どこに」
プレイブック
playbooks/		実行する作業の台本。「どのグループに」「どんなタスクを」実行するかを YAML で書く。「何を」
モジュール個々の作業の実行部品。パッケージ導入は package、ファイル配布は copy など、数千種類が用意済み。「どうやって」

実行時はこの3つを組み合わせて「インベントリの web グループに、このプレイブックを実行して」と指示します。

STEP 3

リポジトリの歩き方

ansible-skeleton のディレクトリ構成です。Ansible には標準的なディレクトリレイアウトがあり、このリポジトリはそれに沿っています。まずは太字の4つだけ押さえれば読めます。

ansible-skeleton/
├── ansible.cfg          # Ansible全体の動作設定（接続方法・ログ出力先など）
├── inventories/         # どこに → 環境ごとのサーバー一覧
│   ├── development/     #   ローカル検証用VM
│   ├── test/            #   テスト環境（ansible.cfg のデフォルト）
│   ├── staging/         #   ステージング環境
│   └── production/      #   本番環境
├── playbooks/           # 何を → 実行する台本
│   ├── ping.yml         #   疎通確認（まずこれを実行する）
│   └── site.yml         #   全体構成の親プレイブック
├── roles/               # 作業の部品集（STEP 5 で解説）
│   └── common/          #   全サーバー共通設定のロール
├── group_vars/          # グループ単位の変数（all.yml は全ホスト共通）
├── host_vars/           # ホスト単位の変数
├── files/ templates/    # 配布するファイル・設定ファイルの雛形
├── library/ filter_plugins/ # 自作モジュール・自作フィルタの置き場
├── collections/         # 追加モジュール集のインストール先
├── requirements.yml     # 依存する追加モジュール集の一覧
└── logs/                # 実行ログ（ansible.log）
POINT

ansible.cfg があるディレクトリで ansible-playbook コマンドを実行すると、この設定が自動で読み込まれます。作業は常にリポジトリ直下で行うのが基本です。

STEP 4

プレイブックを読んでみる

実物を読むのが一番の近道です。疎通確認用の playbooks/ping.yml を見てみます。

playbooks/ping.yml

---
- name: 疎通確認（SSH と Python の到達性チェック）   # ← この台本の説明
  hosts: all                                    # ← インベントリの全ホストが対象
  tasks:                                        # ← 上から順に実行される作業リスト
    - name: ping
      ansible.builtin.ping:                     # ← モジュール「ping」を呼ぶ

    - name: OS 情報を表示
      ansible.builtin.debug:                    # ← モジュール「debug」でメッセージ表示
        msg: "{{ inventory_hostname }} / {{ ansible_facts['distribution'] }}"

読み方はこうです。

  • プレイ — 「hosts: all に対してこのタスク群を実行する」というまとまり。1ファイルに複数書けます。
  • タスク — tasks: 以下の1項目が1作業。それぞれに name（実行時に表示される説明）とモジュール呼び出しを書きます。
  • {{ }} は変数 — 二重波かっこの中は実行時に値が入ります。inventory_hostname（ホスト名）のような組み込み変数と、自分で定義した変数の両方が使えます。
STEP 5

ロール — 作業を部品化する

タスクを全部プレイブックに直書きすると、すぐに巨大で再利用できないファイルになります。そこで Ansible では、ひとまとまりの作業を「ロール」という部品に切り出します。親プレイブック site.yml はロールを呼ぶだけの短さです。

playbooks/site.yml

- name: 全ホスト共通設定
  hosts: all
  become: true          # ← sudo で root 権限に昇格して実行
  roles:
    - common            # ← roles/common/ を丸ごと実行

ロールの中身は役割ごとのディレクトリに分かれていて、Ansible が決まった場所を自動で読み込みます。

roles/common/
├── tasks/main.yml      # 実行するタスク本体（ロールの入口）
├── handlers/main.yml   # 「変更があったときだけ」動く後処理
├── defaults/main.yml   # 変数のデフォルト値（外から上書き可能）
├── vars/main.yml       # 上書きさせない固定の変数
├── files/              # 配布ファイル（users.csv など）
└── meta/main.yml       # ロールの説明・依存関係

common ロールのタスク本体はこの2つです。

roles/common/tasks/main.yml

- name: 基本パッケージをインストール
  ansible.builtin.package:
    name: "{{ common_packages }}"   # ← 変数。デフォルトは [vim]
    state: present                  # ← 「入っている状態」を宣言する書き方

- name: タイムゾーンを設定
  community.general.timezone:
    name: "{{ timezone }}"          # ← Asia/Tokyo
  notify: restart cron              # ← 変更があったらハンドラーを呼ぶ
HANDLER

notify: restart cron は「タイムゾーンが実際に変更されたときだけ、cron を再起動する」という意味です。変更がなければ再起動しません。「設定変更 → サービス再起動」のような後処理は、ハンドラー（handlers/main.yml）に書くのが定石です。

このロールの defaults/main.yml には、files/users.csv を元にした Linux アカウント管理（作成・削除・SSH鍵配置・SFTP用マウント）の設定も定義されています。CSV に1行足せばユーザーが増える、という運用を目指した作りです。

STEP 6

変数と環境の切り替え

「テスト環境と本番環境で接続先だけ違う」を実現するのがインベントリの分割です。このリポジトリでは環境ごとにディレクトリを分けており、実行時に -i で指定するだけで対象環境が切り替わります。プレイブック側は一切変えません。

inventories/development/hosts.yml

all:
  children:
    web:                        # ← 「web」グループ
      hosts:
        almalinux9-test:        # ← ホスト名（~/.ssh/config のエントリ名）
          ansible_user: ec2-user
          ansible_port: 2222

変数は複数の場所に書けて、より具体的な場所が勝ちます。ざっくり弱い順に：

  • roles/*/defaults/ — ロールのデフォルト値（いちばん弱い＝上書きされる前提）
  • group_vars/all.yml — 全ホスト共通（このリポジトリでは timezone: Asia/Tokyo など）
  • group_vars/<グループ名>.yml → host_vars/<ホスト名>.yml — グループ別・ホスト別
  • コマンドラインの -e 指定 — いちばん強い

「デフォルトはロールに置き、環境差分だけをインベントリ側で上書きする」のが基本形です。

STEP 7

実行してみる

このリポジトリでの典型的な流れです。すべてリポジトリ直下（ansible.cfg のある場所）で実行します。

# 0. 初回のみ：依存モジュール集を取得（requirements.yml に定義）
ansible-galaxy collection install -r requirements.yml

# 1. まず疎通確認 — SSH でつながるかを ping.yml で確かめる
ansible-playbook -i inventories/development/hosts.yml playbooks/ping.yml

# 2. ドライラン — 実際には変更せず「何が変わるか」だけ表示
ansible-playbook -i inventories/development/hosts.yml playbooks/site.yml --check --diff

# 3. 本実行
ansible-playbook -i inventories/development/hosts.yml playbooks/site.yml

# 部分実行 — タグ付きタスクだけ流す（例：タイムゾーン設定のみ）
ansible-playbook -i inventories/development/hosts.yml playbooks/site.yml --tags timezone
SAFETY

本実行の前に必ず --check --diff（ドライラン）で変更内容を確認する習慣をつけてください。冪等性のおかげで、実行結果には changed=0（何も変わらなかった）という表示が出ます。「2回目に実行して changed=0 なら、サーバーはあるべき状態になっている」と読めます。実行ログは logs/ansible.log にも残ります。

付録

用語ミニ辞典

用語意味
冪等性何度実行しても結果が同じになる性質。「〜する」でなく「〜の状態にする」と書くことで実現される。
becomesudo などで管理者権限に昇格すること。become: true で root として実行。
ファクト実行時に Ansible が対象サーバーから自動収集する情報（OS種別、IPアドレスなど）。ansible_facts で参照。
コレクションモジュールの配布パッケージ。標準外のモジュール（例：community.general.timezone）はこれで追加する。
タグタスクに付ける印。--tags で「この印のタスクだけ」を部分実行できる。
ハンドラータスクが実際に変更を起こしたときだけ、プレイの最後に1回動く処理。サービス再起動の定番。
ドライラン--check オプション。変更を加えずに「何が変わるはずか」だけを表示する予行演習。
